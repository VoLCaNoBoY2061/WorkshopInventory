# Система учёта компонентов и материалов в мастерской

Каркас WPF-приложения (.NET 8) под Visual Studio, построенный на основе ваших UML-диаграмм
(use case и activity). Хранилище — SQLite-файл `workshop.db`, создаётся автоматически рядом
с exe при первом запуске, сервер БД не нужен.

## Как запустить

1. Откройте `WorkshopInventory.sln` в Visual Studio 2022 (нужна нагрузка ".NET desktop
   development").
2. Дождитесь восстановления NuGet-пакетов (`Microsoft.EntityFrameworkCore.Sqlite`,
   `Microsoft.EntityFrameworkCore.Design`).
3. F5. На экране входа доступны демо-пользователи:
   - `storekeeper` / `1234` — Кладовщик
   - `manager` / `1234` — Руководитель
   - `master` / `1234` — Мастер

   Пароль `1234` захеширован в `DbInitializer` через SHA-256 — не хранится открытым текстом.

## Как диаграммы легли на структуру проекта

| Диаграмма | Элемент | Реализация |
|---|---|---|
| Use case: акторы | Кладовщик / Руководитель / Мастер | `Models/Enums.cs` → `UserRole`, видимость вкладок в `MainWindow` |
| Учёт поступлений, списание, перемещение | Кладовщик | `Models/Receipt.cs`, `WriteOff.cs`, `Movement.cs` + `Services/StockService.cs` |

| Формирование отчётов → просмотр отчётов (`<<включить>>`) | Кладовщик, Руководитель | `Views/ReportsView` (вкладки "Остатки" и "Движение") |
| Просмотр движения, контроль заявок | Руководитель | `Views/ReportsView`, `Views/RequestsView` (Одобрить/Отклонить) |

## Архитектура

```
Models/     — сущности (User, Material, Receipt, WriteOff, Movement, MaterialRequest)
Data/       — AppDbContext (EF Core + SQLite), DbInitializer (тестовые данные)
Services/   — бизнес-логика: AuthService, StockService, RequestService
Views/      — окна и UserControl'ы (код-behind напрямую обращается к сервисам)
```

Сознательное упрощение: вместо полного MVVM с биндингами и командами используется
код-behind, который напрямую вызывает сервисы и обновляет `DataGrid.ItemsSource`. Для
учебного/среднего по размеру проекта это самый быстрый путь без риска поймать ошибки
биндинга. Если нужно перейти на строгий MVVM — вынесите содержимое `Initialize`/обработчиков
кнопок в ViewModel-классы с `ICommand` (`RelayCommand`) и `INotifyPropertyChanged`, View
останется почти без изменений.

## Обновление: несколько складов и автообновление

**Учёт по нескольким складам.** Остаток материала больше не хранится одним числом в
`Material` — вместо этого появилась таблица `MaterialStock` (материал × склад ×
количество). Одному материалу теперь может соответствовать несколько строк — по одной на
каждый склад, где он физически есть.

- На вкладке «Материалы» появился выпадающий список складов, включая пункт «Все склады»
  (сумма по всем). Переключаясь между складами, вы видите именно тот остаток, который
  реально там лежит.
- «Перемещение» в складских операциях теперь списывает количество с одного склада и
  добавляет его на другой, а не просто переписывает единственное поле «Расположение» —
  общий остаток по материалу не теряется и не задваивается.
- В «Приход»/«Списание» тоже нужно указывать склад (можно ввести название нового склада
  прямо в поле — он появится в списках после следующего обновления).
- В «Отчётах» добавлена вкладка «Остатки по складам» — построчный список
  материал/склад/количество, чтобы сразу видеть, где что лежит.
- Заявки мастеров (`RequestService.Fulfill`) по-прежнему закрываются с основного склада
  (`StockService.DefaultLocation`) — если нужный материал лежит только на другом складе,
  кладовщику нужно сначала переместить его на основной. Это сознательное упрощение;
  расширить логику на «взять с любого склада, где хватает» несложно — правка одного
  метода в `RequestService.cs`.

**Автообновление вкладок.** Раньше каждая вкладка загружала данные один раз при входе —
новый материал не появлялся у других пользователей и на других вкладках без перезапуска.
Отдельного "обновить всё" вы не пропустили — этой функции просто не было. Теперь:

- у `MainWindow` появился обработчик `MainTabs.SelectionChanged`, который при переключении
  на вкладку вызывает её `Refresh()` — она заново читает данные из базы;
- на вкладках «Материалы» и «Складские операции» дополнительно есть кнопка «Обновить» —
  для ручного обновления, не переключаясь между вкладками.

Ограничение: если у вас открыто два экземпляра приложения одновременно (например, второй
логин на роль Кладовщика в другом окне), автообновление сработает только при
переключении вкладок в каждом окне — "живого" пуша между окнами нет. Для учебного проекта
этого достаточно; для реального многопользовательского сценария нужен был бы поллинг по
таймеру или SignalR.

## Что стоит доработать дальше

1. **Разграничение прав на уровне данных**, а не только UI (сейчас скрытая вкладка — это
   просто скрытая кнопка, а не защита; для учебного проекта этого достаточно, для реального
   — нет).
2. **Экспорт отчётов** в Excel/PDF (можно взять `ClosedXML` или `QuestPDF`).
3. **История изменений заявки** (кто и когда одобрил/отклонил) — сейчас хранится только
   финальный статус.
4. **Уведомления мастеру** при отклонении заявки — сейчас это просто текст в колонке
   "Комментарий"; можно добавить всплывающее окно/бейдж в интерфейсе Мастера.
5. **На UML**: стоит добавить прецедент «Авторизация» с `<<включить>>` от всех трёх акторов,
   и заменить безымянный блок «меседж» на activity-диаграмме на узел «Уведомление мастеру
   об отказе» с явным переходом на конечное состояние.
